# Zero × Zerox 分步执行计划与审查记录

本文件记录实际执行顺序。每个大步骤必须形成一个可回滚的 Conventional Commit；提交前必须完成三类审查并记录结果：

1. **对抗性审查**：主动寻找数据丢失、重复写入、竞态、旧设备升级失败、隐私泄漏、无障碍回归和性能退化。
2. **代码质量审查**：类型、边界、错误处理、依赖方向、重复逻辑、测试覆盖和可维护性。
3. **注释审查**：注释只解释原因、兼容性约束和迁移规则；删除过时、重复或会误导未来维护者的注释。

1. 统一包管理器和 lockfile。
2. 加入 commitlint、Commitizen、Husky/lint-staged、CODEOWNERS、PR 模板。
3. 加入 lint、format、typecheck、unit test、migration test CI。

## 下一步调整

原计划直接进入完整领域功能，但当前代码审查确认 WatermelonDB v3 结构冲突是更高风险的阻断项。因此先写并运行三条迁移 fixture（fresh、Zero v3、Zerox v3），验证双库受控升级和 BootGate 状态机，再实现收入/二级分类模型；不在没有 fixture 的情况下修改 schema 版本。

### v3 迁移 fixture spike 审查（提交前）

- 实现范围：新增纯函数 `legacySchema.ts`，识别 Zero v3、Zerox v3、目标 v4 和未知形状，输出需要备份的复制动作；没有修改 Watermelon schema 或真实数据库。
- 对抗性审查：同版本号但表/列语义冲突时 fail-closed；Zero/Zerox 互相混合或缺关键列不会被误判为可迁移来源。
- 代码质量审查：新增 4 个 fixture tests；完整 suite 为 17 suites / 227 tests，typecheck 和 lint（75 个既有 warning、0 error）通过。
- 注释审查：注释解释为何先 inspection、为何未知形状必须保守失败，没有承诺静态 SQL 可以条件建列。
- 已完成：`e6aa306` 补 version 非法、缺核心表和目标 v4 缺字段 fixture；下一步实现双库复制器。

### 双库复制状态机审查（提交前）

- 实现范围：新增可注入 `runDualDatabaseUpgrade`，固定 `pending → copying → verified → activated`，未知来源和校验失败进入 `failed`，旧库只在 activate 前保持活动。
- 对抗性审查：金额总和、行数、ID/关系任一校验失败都不能 activate；复制异常和未知 schema 都必须持久化 failed。
- 代码质量审查：新增 3 个状态机测试；完整 suite 为 18 suites / 230 tests，typecheck 通过。
- 注释审查：状态机注释明确旧库保留和 adapter 注入边界，没有把纯函数误称为已完成 SQLite 迁移。
- 未完成项：尚未接入真实 Watermelon adapter、MMKV active-db 切换和崩溃恢复；这些必须在下一提交单独实现。
