# 客观进度与性能评估

更新时间：2026-10-11  
候选分支：`codex/zero-zerox`  
候选提交：`625e6cc`  
对比基线：Zero `d7725cd`、Zerox `a21abd6`

## 结论

按“严格可验收任务”口径，当前整体完成度约 **25%**，合理区间为 **22%–30%**。这个百分比只给已经能在代码和自动化检查中验收的任务计分；迁移契约存在但尚未接入生产、Android 只完成编译、以及保留的 Zero 能力都不会被当成完整的新功能。此前按“包含半成品契约”的宽口径得到约 34%，本文件将两种口径分开，避免把基础设施半成品误报为产品完成度。

需要分开看三个数字：

| 口径           |   当前判断 | 证据                                                                                                                            |
| -------------- | ---------: | ------------------------------------------------------------------------------------------------------------------------------- |
| 工程底座       |     约 58% | 最新依赖已锁定；JS 门禁通过；Android debug 构建通过；只读预检、v4 target、复制验证和驱动契约已存在                              |
| 严格可验收产品 | **约 25%** | 只计算已经有可执行契约和检查的部分；Zero 基线能力保留不等于 Zerox 功能已合并，迁移尚未接入 BootGate，录入和底部导航动画尚未实现 |
| 发布就绪       | 约 22%–25% | Android release 已完成原生编译、Hermes、lint，但没有签名 keystore、设备回归、迁移真机验证、iOS/macOS 验证、E2E 和完整发布 CI    |

当前没有 Android 设备或模拟器连接，也没有采集冷启动 TTI、JS commit、UI FPS/jank、内存或数据库复制耗时。因此不能诚实地给出“比 Zero 快 X%”或“比 Zerox 快 X%”。在取得固定设备和固定数据集的实测结果之前，任何百分比性能结论都会是假精度。

## 当前已验证事实

### 依赖和门禁

- 目标栈已锁定：RN 0.87.1、React 19.3.0、TypeScript 7.0.2、Reanimated 4.7.1、Worklets 0.13.0、React Navigation 7.5/7.20、RTK 2.13.0、FlashList 2.3.3、MMKV 4.3.2、Zod 4.6.5、WatermelonDB 0.28.0。
- `pnpm run typecheck`、ESLint、format、Jest、React Native config 和 Metro bundle 已通过；最近一次完整 Jest 为 39 suites/318 tests。
- Android `:app:assembleDebug` 已通过；release 已通过原生编译、Hermes bundle、lint 和资源处理，在 `packageRelease` 因没有签名配置停止。没有把这个结果误报为可发布 APK。
- 目前 CI 只有 format/lint/typecheck/Jest；原生构建、迁移矩阵、审计、secret scan、E2E 尚未纳入 CI。

### Zero 对比

- Zero `d7725cd` 的最新提交只是 CI 文件调整；它没有提供 FPS、TTI、内存或数据库吞吐基准。其历史 `ef08a1e` 虽名为性能改进，但仓库没有可复现的运行时数字。
- 当前候选与 Zero 最新代码的静态计数相同：FlashList 22、ScrollView 42、FlatList 6；候选有 104 处 `useMemo`、201 处 `useCallback`，Zero 有 103/203。这个结果说明现有列表基线主要继承了 Zero，不能证明候选已经快于 Zero。
- 当前候选 30 个 test/spec 文件、约 2,912 行，Zero 16 个、约 1,831 行；候选的迁移契约和自动化门禁覆盖更强，但测试数量也不能换算成运行时性能，业务功能仍需补收入/AI/动画 fixture 与 E2E。
- 当前候选的报告图表使用自绘 `DonutChart`/`donutGeometry`，没有引入 Zerox 的 `react-native-svg-charts`；几何逻辑有单测。这是依赖和可测试性改进，不是已测得的 FPS 改进。

### Zerox 对比

- Zerox 最新提交 `a21abd6` 的收入、AI 队列和首页快捷入口仍未进入候选生产业务层；当前收入/AI/中文/二级分类的可运行功能吸收度接近 0%。
- Zerox 的 `1fd3ed3 Improve transaction list performance` 把按日期分组的嵌套渲染改为 header + transaction 的扁平 FlashList 数据。当前候选仍是 Zero 的按日期分组结构：在同一天 1000 笔交易时，一个顶层 FlashList item 可能携带整组 1000 行，而 Zerox 约有 1000 个交易顶层 item 加日期 header。这是可验证的结构性差异，但没有设备 FPS 数据，不能换算成百分比。
- 当前候选 `src/screens/HomeScreen/useHome.ts` 仍会在每次 focus 先失效 expense cache 再查询；Zerox 已把 focus 失效去掉，只在显式刷新时失效。候选尚未吸收该优化，因此这条路径存在可测的额外数据库/Redux 工作。
- Zerox 源码静态风险更高：`any` 约 10 处、旧式 raw fetch 约 58 处，并且 AI runner 是逐条写入、没有统一事务和幂等键。候选目前没有 AI 代码，不能把“尚未引入风险”说成“AI 已优化完成”。

## 目前能说和不能说的性能结论

现在能说：

1. 依赖版本已达到用户指定的最新目标栈。
2. 候选保留了 Zero 的 FlashList/自绘图表/缓存和测试基础，并增加了更严格的 JS 门禁与迁移契约。
3. Zerox 扁平交易列表和 focus cache 优化是下一轮应吸收、重写并测量的明确目标。

现在不能说：

1. 不能说 RN、Reanimated、FlashList 升级自动带来了固定百分比性能提升。
2. 不能说候选已经比 Zero 或 Zerox 更快；目前没有同设备、同数据、同构建模式的实测数据。
3. 不能说底部导航已经丝滑；自定义 Tab bar、AddEntry 单路由和 UI 线程动画目前仍为 0%。

## 下一次性能事实验收

在 Android API 35/36 的同一台设备上，构建 Zero `d7725cd`、Zerox `a21abd6` 和候选 release。使用相同的 100/1,000/10,000 行数据库 fixture，并分别测试 1 天/100 天分布。每项至少 30 次，记录 median/P95：

- 冷启动到 BootGate ready 的 TTI；
- React Profiler 的 JS commit duration；
- Reanimated `useFrameCallback` 或 Perfetto 的 UI FPS/jank；
- `dumpsys meminfo` 的峰值和稳定内存；
- 月份查询、列表首屏和迁移复制的 wall time；
- 交易列表顶层 item 数、实际渲染行数和重复查询次数。

只有候选在数据正确性不回退的前提下，P95 不高于 Zero 基线，并且对 Zerox 的目标功能完成同等测试，才能在后续报告中使用“性能正向提升”或具体百分比。

## 下一步优先级

下一轮继续 P0/P1，而不是提前做视觉动画：先补齐 durable backup/discard、source fingerprint、target freshness 和状态机/BootGate 接线；随后吸收 Zerox 的扁平交易列表与 focus cache 优化，先做纯函数/fixture 测试，再接入设备基准。AddEntry 和底部 Tab 的 Reanimated 4.7 动画放在数据与导航状态稳定后实现，避免用动画掩盖查询、挂载和路由切换问题。
