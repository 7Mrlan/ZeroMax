# 客观进度与性能评估

更新时间：2026-10-12  
候选分支：`codex/zero-zerox`  
候选提交：`8d15bfb`
对比基线：Zero `d7725cd`、Zerox `a21abd6`

## 结论

按“严格可验收任务”口径，当前工程契约完成度约 **62%–69%**，发布就绪度约 **34%–42%**。工程契约只计入已有代码、测试或静态门禁的部分；发布就绪度额外要求迁移崩溃、Android E2E/无障碍、iOS 设备、签名和真实性能报告。两者都不是运行时性能百分比，也不把 Zero 已有基线能力重复计作新功能。

需要分开看三个数字：

| 口径               |       当前判断 | 证据                                                                                                                                                                                                                                   |
| ------------------ | -------------: | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 工程底座           |         约 67% | 最新依赖已锁定；JS 门禁通过；Android JSI debug build 与 API35 fresh v4 冷启动通过；只读预检、v4 target、复制验证、恢复和 iOS source contracts 已存在                                                                                   |
| 严格可验收工程契约 | **约 60%–67%** | Android P0、v4 数据域/export v5、收入/分类/AI 核心、统一录入/动画、扁平流水、CI/E2E 契约和 iOS source contracts 已落地；设备、签名和真实性能仍阻断发布                                                                                 |
| 发布就绪           |     约 34%–42% | 静态门禁、JSI debug artifact、API35 fresh v4 和空 Zero v3 启动已有；代表性 Zero/Zerox 的旧 native-writer smoke 需按 `9eeabdf` handoff 协议复测，大规模/崩溃恢复仍阻塞，没有 signed AAB、E2E、iOS Pods/设备或 `performance/latest.json` |

当前 API35 x86_64 模拟器已提供 fresh v4/JSI 和重启 Welcome 证据；代表性 Zero/Zerox 旧 writer smoke 尚未按新 verified→activated coordinator 协议复测，也没有采集冷启动 TTI、JS commit、UI FPS/jank、内存或数据库复制耗时。因此不能诚实地给出“比 Zero 快 X%”或“比 Zerox 快 X%”。在取得固定设备和固定数据集的实测结果之前，任何百分比性能结论都会是假精度。

## 当前已验证事实

### 依赖和门禁

- 目标栈已锁定：RN 0.87.1、React 19.3.0、TypeScript 7.0.2、Reanimated 4.7.1、Worklets 0.13.0、React Navigation 7.5/7.20、RTK 2.13.0、FlashList 2.3.3、MMKV 4.3.2、Zod 4.6.5、WatermelonDB 0.28.0。
- `pnpm run typecheck`、ESLint、format、Jest、React Native config 和 Metro bundle 已通过；最近一次完整 Jest 为 50 suites/372 tests，迁移 19 suites/100 tests，导出 4 suites/39 tests。
- Android `:app:assembleDebug` 已在临时 JDK17/SDK37/NDK28 主机环境真实通过，453 tasks、artifact manifest/dex/arm64 检查和 JSI source contract 通过；API35 x86_64 fresh v4 与空 Zero v3 冷启动、marker ownership 和重启 Welcome UI 已实证 JSI 加载与 fresh target activation。`9eeabdf` 后 native writer 在真实 SQLite commit+close 后只写 `verified` marker，代表性 Zero/Zerox fixture 的历史 activated-marker 记录需按新 coordinator 协议复测；因此仍没有把 debug 结果误报为大规模迁移、崩溃恢复或可发布 APK。
- Android release packaging 也已用一次性临时 keystore 完成 `assembleRelease`（740 tasks）和 v2 `apksigner verify`；临时材料已清理。该证据只证明打包链路，不等于生产签名、真实设备 release、迁移恢复或性能通过。
- CI 已有 format/lint/typecheck/Jest、migration/export matrix、secret scan、audit、commitlint、Android debug artifact job；Maestro 流程已入库但没有设备执行证据，性能 validator 也不生成报告。

- API35 x86_64 单次规模 smoke：固定 Zero v3 fixture 的 5,000 条 expenses 已复制到 v4，target read-back 行数为 5,000、历史记录显示 marker activated、无 `database disk image is malformed`；该记录发生在 marker handoff 修复前，不能替代新协议的完整编排证据；这是单点候选样本，不是 P50/P95 或相对 Zero/Zerox 性能结论。

### Zero 对比

- Zero `d7725cd` 的最新提交只是 CI 文件调整；它没有提供 FPS、TTI、内存或数据库吞吐基准。其历史 `ef08a1e` 虽名为性能改进，但仓库没有可复现的运行时数字。
- 当前候选与 Zero 最新代码的静态计数相同：FlashList 22、ScrollView 42、FlatList 6；候选有 104 处 `useMemo`、201 处 `useCallback`，Zero 有 103/203。这个结果说明现有列表基线主要继承了 Zero，不能证明候选已经快于 Zero。
- 当前候选 30 个 test/spec 文件、约 2,912 行，Zero 16 个、约 1,831 行；候选的迁移契约和自动化门禁覆盖更强，但测试数量也不能换算成运行时性能，业务功能仍需补收入/AI/动画 fixture 与 E2E。
- 当前候选的报告图表使用自绘 `DonutChart`/`donutGeometry`，没有引入 Zerox 的 `react-native-svg-charts`；几何逻辑有单测。这是依赖和可测试性改进，不是已测得的 FPS 改进。交易流水已改为日期 header + transaction/pendingDelete 的单一 FlashList 数据源，仍需设备基准证明回收和 jank 改善。

### Zerox 对比

- Zerox 最新提交 `a21abd6` 的收入、二级分类、中文/英文 key、AI parser/network/queue/privacy 已进入候选生产代码；AI queue 现在有显式处理、queued cancel 和 running AbortSignal，批量撤销、设备网络回归和完整业务回归仍未完成，不能把核心契约当作全功能完成。
- Zerox 的 `1fd3ed3 Improve transaction list performance` 把按日期分组的嵌套渲染改为 header + transaction 的扁平 FlashList 数据。当前候选已采用同一扁平数据模型并保留稳定 kind:id 与三秒撤销；这是结构性改进，但没有设备 FPS 数据，不能换算成百分比。
- 当前候选已把 expense/income cache 改为按月份 keyed cache 并以 requestId 拒绝过期响应；是否优于 Zero/Zerox 仍须同设备、同 fixture 基准，不能由代码结构推导百分比。
- 首页 focus 现在复用 fulfilled month cache，只在显式下拉刷新时失效并重新查询；这消除了 tab 切换时的空列表窗口，但仍需要设备基准验证查询次数和感知延迟。
- 首页按月并行加载支出与收入并以 kind:id 合并流水；预算/已花费保持支出语义，年份缓存合并两表。该行为正确性已有数据域契约，运行时查询和渲染成本仍须设备实测。
- Reports 同样按月加载收入并展示合计，预算和支出图表不混入收入；这是业务语义修复，不是性能百分比。
- 中文资源已与英文资源保持 leaf key parity，主要高频页面已翻译；这证明语言切换覆盖面，不代表文案质量或运行时性能提升。
- Zerox 源码静态风险更高：`any` 约 10 处、旧式 raw fetch 约 58 处，并且 AI runner 是逐条写入、没有稳定幂等键。候选已将 AI parser/network/queue/writer 重写为 Zod、secure store 和稳定记录 ID；跨存储原子性和设备网络错误仍需实测。

## 目前能说和不能说的性能结论

现在能说：

1. 依赖版本已达到用户指定的最新目标栈。
2. 候选保留了 Zero 的 FlashList/自绘图表/缓存和测试基础，并增加了更严格的 JS 门禁与迁移契约。
3. 候选已吸收 Zerox 的扁平交易列表思路并保留稳定 kind:id、三秒撤销和收入删除语义；当前仍没有运行时对照证据。

现在不能说：

1. 不能说 RN、Reanimated、FlashList 升级自动带来了固定百分比性能提升。
2. 不能说候选已经比 Zero 或 Zerox 更快；目前没有同设备、同数据、同构建模式的实测数据。
3. 不能说底部导航已经丝滑；自定义 Tab bar、AddEntry 单路由和 UI 线程动画已有代码契约，但没有真实设备帧率/jank 证据。

## 下一次性能事实验收

在 Android API 35/36 的同一台设备上，构建 Zero `d7725cd`、Zerox `a21abd6` 和候选 release。使用相同的 100/1,000/10,000 行数据库 fixture，并分别测试 1 天/100 天分布。每项至少 30 次，记录 median/P95：

- 冷启动到 BootGate ready 的 TTI；
- React Profiler 的 JS commit duration；
- Reanimated `useFrameCallback` 或 Perfetto 的 UI FPS/jank；
- `dumpsys meminfo` 的峰值和稳定内存；
- 月份查询、列表首屏和迁移复制的 wall time；
- 交易列表顶层 item 数、实际渲染行数和重复查询次数。

只有候选在数据正确性不回退的前提下，P95 不高于 Zero 基线，并且对 Zerox 的目标功能完成同等测试，才能在后续报告中使用“性能正向提升”或具体百分比。

## 下一步优先级

性能 validator 现在还要求 device/build/fixtures/collectionCommand、每项至少 30 个 raw samples，并阻断候选 P95 相对 Zero 超过 5%；它不生成样本，也不接受静态 fixture 作为真实测量。下一轮优先执行 Android 迁移/E2E/签名/性能矩阵和 iOS 外部 smoke，再将结果写入 `performance/latest.json`。
