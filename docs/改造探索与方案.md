### 2.1 版本事实和需要修正的预期

用户提供的目标版本表可以作为候选版本表，但不能直接视为可安装组合。用户已明确要求直接采用最新稳定技术，因此当前目标锁定为 **RN 0.87.1 + React 19.3.0**，不回退到 React 19.2.3。RN 的 `react: ^19.2.3` peer 范围只表示依赖声明允许 19.3，不等于 React 19.3 已完成原生 renderer 验证；React 19.3 的真实兼容性必须在 Hermes/Fabric、Android/iOS debug/release smoke 中单独验收。

RN 0.87 带来 Strict TypeScript API，深层导入会被视为类型错误，且移除了部分旧 API；这不是只改 `typescript` 字段即可完成的升级。RN 0.87 的官方说明见 [React Native 0.87](https://reactnative.dev/blog/2026/08/11/react-native-0.87)，版本支持矩阵见 [React Native versions](https://reactnative.dev/)。WatermelonDB 模型使用 legacy decorators，TS7 升级要保留 legacy decorator 配置并增加 model/schema smoke test。

TypeScript 7.0.2 使用原生 Go 编译器，但 `typescript-eslint`、Jest 等生态仍可能依赖 TS 6 API。方案采用“双工具链”过渡：TS7 负责类型检查，TS6 兼容包供 ESLint/Jest 等工具使用，直到生态完全支持 TS7。TS7 的约束来自 [TypeScript 7 公告](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)。

WatermelonDB 0.28.0 暂时保留，但必须做独立的新架构 spike。其 RN New Architecture/JSI/bridgeless 的生产兼容性仍有公开问题，不能把数据库迁移和 RN/UI 大改放在一个不可回退的提交中。迁移规则参考 [WatermelonDB migrations](https://watermelondb.dev/docs/Advanced/Migrations)。

## 3. 两个系统的现状

### 3.1 Zero 官方维护线

Zero v2.6.6 的分层如下：

```text
App/bootstrap
  ├─ initBackend、错误边界、全局错误日志、Redux Persist
  └─ NavigationContainer
       ├─ MainStack（引导 / 主应用）
       └─ HomeStack（底部 Tab + 业务详情 Stack）
            └─ screens/index.tsx + use*.ts
                 └─ Redux slices / thunks（查询缓存）
                      └─ WatermelonDB services（查询、写入、批量）
                           └─ models / schema / migrations
                                └─ SQLite + JSI
```

横切能力包括 Theme/Dialog/i18n/ActionSheet、MMKV 偏好设置、导入导出、后端数据迁移和通用 utils。

官方线的主要优点：

- `src/backend/export` 有 Zod 校验、导出版本、v0→v4 升级器、CSV 导出和导入规划器。
- `src/watermelondb` 已加入预算表、预算查询服务、批量导入恢复和诊断页面。
- v2.4.2 和 v2.6.6 之间完成了 i18n、区域化金额、FlashList/手势性能、WCAG 颜色、adaptive daily budget、自绘 donut chart 等维护提交。
- `App.tsx` 有错误边界、初始化错误记录、MigrationWarningBanner 和恢复路径。
- 约 16 个测试文件、约 1831 行测试，覆盖 import/export、迁移、金额/日期/预算/验证和部分 service。

官方线的局限：

- 只支持支出，没有收入表和收入分类；`categories` 没有 `parent_id/kind`。
- README 的技术栈描述落后于 package.json（README 仍写 RN 0.84）。
- 只有 typecheck GitHub Actions，没有完整的 lint/test/build/安全门禁。
- 底部 Tab 只自定义了 `tabBarButton`，没有切换指示器或 UI 线程动画。
- `src/i18n/locales` 当前只有 `en.json`，中文需要从 Zerox 移植。
- 仍有若干 `any` 和 RN 0.87 Strict API 迁移点，例如 `useSwipeTutorial.ts` 使用 `InteractionManager.runAfterInteractions`。
- Home/Reports 月份切换直接复用单个 Redux entity cache，没有 active query key/requestId gate；快速切月时旧月份可能短暂显示。统一 `monthDataByKey` 或 requestId gating，不能只在 focus 时 invalidate。
- `backend/schema-snapshot.json` 仍落后实际 schema，升级前必须补齐 v3/v4 snapshot 并在 CI 校验 schema、migration、model 三者一致。
- Zerox 债务、错误边界和部分校验文案仍硬编码中文；如果保留英文入口，必须把用户可见文案全部收敛到 i18n，并把英文完整度纳入验收。

### 3.2 Zerox 二次开发线

Zerox 在同一基础架构上加入：

- AI 自然语言快速记账：OpenAI-compatible API、MMKV 本地队列、App 重启恢复、失败重试和撤销批次。
- 独立收入表、收入分类、收入页和收入统计；债务功能嵌入收入页分段。
- `categories.parent_id` 二级支出分类和 `kind = expense|income`。
- 中文优先、语言上下文、主题色配置和中文默认分类。
- 首页混合展示支出和收入流水，收入使用不同金额颜色。
- 针对列表滚动、AI 输入、防抖存储和默认分类批量创建的性能文档与实现。

主要模块：

- `src/services/aiSettingsService.ts`
- `src/services/aiExpenseParser.ts`
- `src/services/aiAutoExpenseTaskService.ts`
- `src/services/aiAutoExpenseRunner.ts`
- `src/components/atoms/AiAutoExpenseRecovery.tsx`
- `src/screens/AiQuickExpenseScreen`
- `src/screens/AiExpenseQueueScreen`
- `src/screens/AiExpenseQueueDetailScreen`

AI 网络调用还需要补充 AbortController/超时、响应大小上限、HTTPS 提示、受控重试、Zod response schema 和取消入口；当前 parser 直接 fetch 用户配置的 Base URL，服务层有 `any` 和无运行时校验。

- `src/screens/IncomeScreen`
- `src/watermelondb/services/incomeService.ts`

Zerox 的主要问题：

- 其 schema v3 与 Zero schema v3 不是同一个结构：Zerox 有收入和二级分类，Zero 有预算和支出备注。
- Zerox 的导出格式也使用 v4，但 v4 的语义不同：Zerox 是收入/分类字段，Zero 是预算字段。直接互相导入会造成数据丢失或校验错误。
- `ExpenseEntry.tsx:184` 和 `IncomeEntry.tsx:114` 使用 `replace()` 切换页面；两个页面是不同的路由和不同的表单实例。
- 底部导航依旧是静态 `Tab.Navigator`，没有丝滑切换动画。
- 两仓库都同时存在 `bun.lock`/`package-lock.json` 痕迹或文档混用 npm/Bun，升级前必须只选一个包管理器并删除另一套锁文件，否则 CI 和本地解析结果会漂移。
- Zerox 的 `app.json`、Android namespace/applicationId、iOS target/Info.plist 仍有 `zero`/`com.anotherwhy.zero` 残留。产品名称和 bundle/application ID 必须在发布前确定；若要兼容商店升级，不能直接改 applicationId，应设计原生迁移和深链兼容。
- Zerox 没有官方线完整的预算、CSV、诊断、导入原子恢复和部分测试覆盖。
- Zerox Reports 仍有 `react-native-svg-charts` 与 `ScrollView + map` 路径；统一实现优先移植 Zero 的自绘 `DonutChart`/几何测试和 FlashList，避免带回旧图表依赖。滑动删除同时采用带 VoiceOver/TalkBack action 的实现。
- `App.tsx:24-26` 通过 `useEffect` 异步启动 `initBackend`，但 Navigation 和 AI 恢复组件会同时首屏挂载；数据库懒加载与数据迁移可能竞态。生产环境还会吞掉迁移异常。统一实现必须增加 `BootGate`，迁移成功后再挂载业务树，失败显示可重试页面。
- Zerox 的 `migration_003_category_income_foundation` 硬编码中文旧分类名；Zero 旧默认分类包含英文名称，直接升级可能把英文分类全部落到中文“其他·其他”。迁移应使用稳定旧 ID/多语言映射并覆盖中英文 fixture。
- AI 队列任务恢复和自动创建目前缺少“任务条目 → 账单”的幂等键；进程在数据库写入成功、任务状态更新前崩溃时，重启可能重复入账。统一实现要为每个 AI 条目保存 idempotency key，并在一次事务内写账单和任务结果。
- Zero 原生 Android Manifest 默认不声明网络权限，而 Zerox AI 需要调用云端 OpenAI-compatible 接口。合并 AI 时必须把网络权限、隐私披露、用户显式开关和脱敏策略作为产品决策，不能隐式改变 Zero 的离线安全边界。
- Zerox `ExpenseEntry` 的 `isValid` 只校验标题和金额，没有把“已选分类”纳入按钮禁用条件；统一录入页应让校验结果和提交 use-case 完全一致，并给出可理解的错误提示。
- Zerox 旧导入以裸分类名称建立 `categoryIdMap`；支出子类、支出父类和收入分类可能同名，后写值会覆盖前写值，导致收入账单关联到支出分类。统一导入必须使用 `kind + parentName + name` 复合键，并校验目标分类类型。

## 4. 功能取舍

### 4.1 采用 Zero 的能力

以 Zero v2.6.6 作为维护基线，保留并移植：

- WatermelonDB JSI、数据库错误处理和懒加载 Proxy。
- 预算、adaptive daily budget、CSV 导出、JSON 导入/导出版本升级器。
- WCAG 颜色迁移、数据清洗、诊断页和错误日志。
- FlashList 单条记录虚拟化、SwipeableRow/撤销删除、DonutChart 和新的金额/日期工具。
- Zero 最新 package/native 配置作为 RN 升级起点，但逐项回归，不整支覆盖 Zerox。

### 4.2 采用 Zerox 的能力

- 中文 `zh-CN` 主界面与中文默认分类；同时保留英文和语言扩展能力。
- 独立收入记录、收入分类、收入统计和债务分段。
- 二级支出分类：父类/子类、统计聚合、默认分类和旧分类映射。
- AI 快速记账队列、恢复、失败详情、重试和撤销。
- 主题色偏好、收入和支出统一的首页流水视图。

### 4.3 暂不做的结构性大改

第一阶段不直接把 `expenses` 和 `incomes` 复制到全新的 `transactions` 表。这样会同时改变 WatermelonDB 迁移、旧 ID、关系、导入导出和所有查询，风险远高于当前需求。

第一阶段保留两张表，在 service/repository 层提供统一的 `TransactionRecord` 视图，并给每条记录补充 `kind`。待迁移、统计和 AI 稳定后，再评估真正的统一表和转账模型。

## 5. 闪屏根因与目标实现

### 5.1 首页记账/收入切换的根因

当前流程是：

```text
ExpenseEntry
  └─ 点击“收入”
       └─ StackActions.replace('AddIncomeScreen')
            └─ 销毁整个 ExpenseEntry
                 └─ native-stack 执行路由 transition
                      └─ 重建 IncomeEntry、分类查询、输入状态和布局
```

证据：

- [ExpenseEntry.tsx:176-190](/home/lights/文档/ChatGPT/zero记账/zerox/src/components/molecules/ExpenseEntry.tsx:176) 调用 `replace('AddIncomeScreen')`。
- [IncomeEntry.tsx:110-126](/home/lights/文档/ChatGPT/zero记账/zerox/src/components/molecules/IncomeEntry.tsx:110) 调用 `replace('AddTransactionsScreen')`。
- [HomeStack.tsx:143-150](/home/lights/文档/ChatGPT/zero记账/zerox/src/navigation/HomeStack.tsx:143) 将两个页面注册为不同的 Stack screen。

所以问题不只是动画参数，而是页面生命周期被替换。修复目标是一次挂载、局部切换、表单状态稳定。

### 5.2 推荐实现

新增一个 `AddEntryScreen` 和一个 `EntryMode`：

```ts
type EntryMode = 'expense' | 'income';
```

`AddEntryScreen` 只挂载一次，外壳共享 Header、金额、日期和提交按钮；支出/收入只替换分类区域、校验规则和提交 use-case。切换按钮只更新本地 mode：

- Reanimated `useSharedValue` 驱动 active indicator 的 `translateX/width`。
- 表单内容使用 150–220ms 的 opacity + translateY 或 `Layout` 动画。
- 当前输入状态按 mode 保留，来回切换不会丢标题、金额、日期和已选分类。
- 不调用 `replace`，不启动 native-stack transition。
- `startTransition` 只用于低优先级列表/分类派生计算，不用于导航。

如果必须兼容旧深链，保留 `AddTransactionsScreen` 和 `AddIncomeScreen` 作为薄包装，统一导航到 `AddEntryScreen` 并传入初始 mode；包装页面本身不再持有表单。

### 5.3 底部导航动画

当前 `HomeStack.tsx` 只设置 `tabBarButton` 和颜色，未提供动画。推荐使用自定义 `tabBar`：

- 每个 Tab 维护稳定的 `key` 和测量宽度。
- Reanimated shared value 在 UI 线程上移动 active pill/indicator。
- 图标使用 scale/opacity，文字使用轻微 translateY；动画 180–240ms，`Easing.out(Easing.cubic)`。
- 保持 Tab screen mounted，切换只改变焦点，避免重新查询和白屏。
- 先使用 React Navigation 内置 `animation: 'fade'` 或 `shift` 做基线，再替换为自定义 tab bar。
- 为重复点击、返回栈、键盘弹出、Safe Area 和 reduce motion 提供测试。

React Navigation 7.5.0 与 bottom-tabs 7.20.0 的版本需要按包分别锁定，不能把所有 `@react-navigation/*` 都写成 7.5.0。参考 [bottom-tab navigator](https://reactnavigation.org/docs/bottom-tab-navigator/)。

## 6. 数据模型和迁移策略

### 6.1 目标模型（第一阶段）

保留现有表名和主键，合并字段：

```text
users
categories: name, category_status, user_id, icon, color, parent_id?, kind
expenses: title, amount, description?, category_id, user_id, date
incomes: title, amount, category_id, user_id, date
currencies
debtors
debts
budgets
```

规则：

- 老 Zero 支出保留 `description`，UI 可以暂不显示，但导入/导出不能丢失。
- 老 Zerox 支出没有备注，迁移后 `description` 为空。
- 老 Zero 分类补 `kind = expense`、`parent_id = null`。
- 老 Zerox 分类保留 `kind/parent_id`。
- 老 Zero 用户补建 `incomes` 表但不生成虚假收入。
- 老 Zerox 用户补建 `budgets` 表但不生成预算。
- `Category` 必须同时声明 `expenses` 和 `incomes` 关联，`User` 必须同时声明所有 children。

### 6.2 schema 版本处理

两个项目都把 WatermelonDB schema 设为 v3，但 v3 结构不同。统一版本必须升到 v4，并且永远不能修改已经发布的 v1/v2/v3 migration。

迁移 v4 必须覆盖两条路径：

1. Zero v2.6.6 v3 → v4：添加 `categories.parent_id/kind`、创建 `incomes`，保留 `expenses.description`，保留 `budgets`。
2. Zerox v1.0.0 v3 → v4：创建 `budgets`，保留已有 `categories.parent_id/kind` 和 `incomes`，为没有该列的旧 Zerox fresh schema 补 `expenses.description`（optional），保留 `expenses` 数据。

因为两条路径的旧 schema 版本号相同，不能简单写一组无条件 `addColumns`。WatermelonDB migration step 会生成静态 SQL，SQLite 也不能用 `ALTER TABLE ADD COLUMN IF NOT EXISTS` 解决重复列问题。因此方案采用 **preflight + target schema**，不把动态分支伪装成普通 v4 migration：

- 默认采用双库受控升级：旧库保持原 dbName，新建 v4 目标库；只读 inspection 导出原始行，按来源识别后用单 writer/batch 导入目标库。
- 导入完成后校验行数、金额总和、ID/关系、`_status/_changed`、索引和重新打开读写；只有校验成功才在 MMKV 将 active db 标记切换到目标库，旧库保留为恢复备份。
- 状态持久化为 `pending → copying → verified → activated`，崩溃时按状态恢复或继续使用旧库；主界面在迁移未完成/失败时阻塞并提供重试。
- 只有在真实 0.28 JSI fixture 证明同库 preflight 安全后，才考虑用静态 v4 migration；绝不能依赖无法表达条件分支的 `unsafeExecuteSql` 假设，也不能静默清库。
- 必须保留 Zero 已发布的 v1/v2/v3 migration 覆盖路径；WatermelonDB 找不到连续迁移路径时可能走 reset 行为。启动前检测未知 schema/version，进入阻塞恢复页，不能让 adapter 默认清空用户数据。
- 迁移完成后校验每张表的行数、外键引用、金额总和和收入/支出计数，失败时保留备份并阻止进入主界面。

固定 fixture：Zero v3 必须保留用户/分类/支出备注/预算的 ID、`_status`、`_changed` 和金额，补 `kind='expense'`、空 `parent_id` 与空 `incomes`；Zerox v3 必须保留父子分类、收入和金额，补可选 `description` 与空 `budgets`。故障注入时应验证事务回滚、`user_version` 不前进、原表不变，修复后重试成功。

WatermelonDB 官方说明明确要求迁移与 schema 同步、测试“旧安装升级”和“全新安装”两条路径，并提供 `unsafeExecuteSql` 扩展点；相关规则见 [Migrations](https://watermelondb.dev/docs/Advanced/Migrations)。

### 6.3 导入导出版本

Zero 与 Zerox 都使用 export v4，但字段语义不同，不能继续共用 v4。统一项目应：

- 保留现有 v0→v4 升级逻辑，不修改历史步骤。
- 新统一格式发布为 **v5**，同时包含 `budgets`、`incomes`、`kind`、`parentName` 和 `description`。
- v4 Zero 文件：补 `incomes: []`、保留 budgets/description。
- v4 Zerox 文件：补 `budgets: []`、补空 description。
- 导入采用 Zod schema + 纯函数 upgrader + 单 writer/batch 原子恢复。
- 增加 round-trip、跨版本、重复分类、缺失引用、损坏 JSON 和中断恢复测试。

## 8. 代码结构改造

### 8.1 交易流水扁平 FlashList 审查（2026-10-12，候选 HEAD `9eeabdf`；此前 `cd99b77` 为历史快照）

当前候选的 `src/components/molecules/TransactionList.tsx` 仍把同一天的记录放在一个顶层 `TransactionItem` 中，再由该组件用 `expenses.map()` 渲染所有行。这个结构有两个可验证的问题：

- FlashList 只能回收日期组这一层；同一天有 1000 笔记录时，单个顶层 item 仍会创建 1000 个子行，首屏和回收粒度都受最大全日组大小影响。
- 删除撤销状态被放在日期组内部，并依赖 `useRecyclingState`。组被回收或日期顺序改变时，延迟删除、总额和行身份的关联需要额外证明；列表 key 也只有日期，不能表达支出/收入同 ID 的复合身份。

对照 Zerox `1fd3ed3` 的 flat list 改法，统一实现采用单一 FlashList 数据模型：每个日期先产生一个 `header` item，再为每笔记录产生一个 `transaction` 或 `pendingDelete` item。item key 使用 `kind:id`，日期 header 使用 `header:YYYY-MM-DD`，同日排序以完整 ISO 日期后按稳定复合 key 打破平局。扁平化必须是纯函数，输入 pending-delete map 后保持去重、排序、日期 header 和待撤销记录的可见性，方便单元测试。

本轮保留 Zero 现有“3 秒内撤销、超时才永久删除”的语义，不照搬 Zerox 立即删除后再创建新 ID 的实现；后者会改变记录主键、可能丢失支出备注，且崩溃窗口更难恢复。支出和收入使用同一扁平数据契约：收入记录至少能正确展示金额符号/分类并走 `deleteIncomeById`，在没有收入编辑路由时不得伪造导航目标。当前主界面仍主要提供支出数组，因此这次集成不宣称已经完成首页收入查询合并。

对抗性审查结论：扁平模型不能自动证明设备 FPS 或内存提升；必须在固定 Android 设备、相同数据 fixture 和 30 个原始样本下测量。测试先锁定纯函数契约（空列表、跨日排序、同日稳定排序、支出/收入同 ID、pending-delete 替换/去重），再验证组件的 header/row/pending 渲染和无障碍 action 不回退。详见 `src/components/molecules/__tests__/transactionListData.test.ts` 与性能报告的列表基准章节。

保留现有目录习惯，但在 Redux 和 WatermelonDB 之间增加明确的 repository/use-case 层：

```text
src/domain/
  transaction/
    types.ts
    repository.ts
    useCases.ts
  category/
  budget/
  ai/
src/data/
  watermelon/
  mmkv/
```

约束：

- UI 不直接构造 `Q.where`，查询和写入通过 repository/use-case。
- 支出、收入、AI 入账、撤销和导入都走同一套金额/日期/分类边界校验。
- Redux 只存查询缓存、加载状态和 UI 状态；WatermelonDB 是账本事实来源。
- `TransactionRecord` 明确 `kind`、`amount`、`categoryId`、`occurredAt`、`source`，避免首页到处使用 `any`。
- 统一 navigation param list；删除 `any` 的 route 和 `dayTransactions` 类型。
- 统一 i18n key，新增 `zh-CN`、`en`，后续可加 `zh-TW`；语言、日期、数字和货币偏好不进入账本导出。
- 增加 `BootGate`/`MigrationStatus`，把 WatermelonDB schema migration、MMKV data migration、AI queue recovery 串成可观测启动状态。
- AI 解析抽象为可插拔 `AiParser`；默认不上传完整账本，云端调用需要显式同意、脱敏、网络权限和设置页说明，API Key 继续只存本地安全存储。

## 9. 质量、提交和发布规范

### 9.1 Git 提交

使用 Conventional Commits + Commitizen：

```text
feat(nav): add animated bottom tab indicator
fix(entry): keep form state when switching transaction mode
refactor(db): add v4 compatible schema migration
perf(list): preserve FlashList cache on tab focus
test(db): cover Zero and Zerox upgrade paths
build(deps): upgrade React Native toolchain
ci: add migration and typecheck matrix
docs: record merge decisions
```

允许 type：`feat`、`fix`、`refactor`、`perf`、`test`、`build`、`ci`、`docs`、`chore`、`revert`；scope 使用 `nav`、`entry`、`db`、`ai`、`deps` 等稳定词。

提交前门禁：

- `commit-msg`: commitlint
- `pre-commit`: lint-staged（ESLint/Prettier/类型快速检查）
- `pre-push`: typecheck + unit tests + migration contract tests
- 禁止提交 API Key、数据库导出、构建产物、日志、Pods/Gradle 缓存和签名文件。

### 9.2 CI/CD

GitHub Actions 分层：

1. `lint`: ESLint、Prettier、依赖审计、secret scan。
2. `typecheck`: TS7 tsc；并行 TS6 工具链检查。
3. `unit`: Jest、纯函数、Zod、AI parser、export/import、Watermelon service mock。
4. `migration`: fresh schema、Zero v3→v4、Zerox v3→v4、export v0→v5。
5. `android`: RN debug/release assemble、API 35/36、Hermes/Fabric smoke。
6. `ios`: macOS Xcode build、Hermes/Fabric smoke。
7. `e2e`: Detox/ Maestro 覆盖录入切换、底栏、导入恢复、AI 队列恢复。

发布采用 release-please 或 semantic-release 自动生成 CHANGELOG；每个版本必须包含数据库/导出格式变化、升级风险和回滚说明。

### 9.3 当前可执行的 Android CI 出口

即使没有本机 Android SDK，CI 仍可以提供一条可重复的原生静态出口：在 `ubuntu-latest` 使用 JDK 17 和锁定的 pnpm lockfile，执行 `:app:assembleDebug`，随后运行 `scripts/check-android-artifact.js` 检查 APK 是否包含 manifest、DEX、arm64 原生库且没有签名材料，并上传 APK 供后续人工安装。本机现已另有 JDK17/SDK37/NDK28 和 API35 x86_64 模拟器证据；这些证据证明 JSI fresh v4 冷启动，但都不证明迁移崩溃恢复、帧率、16 KB 页面运行时或 release 签名。

release AAB、真实设备安装、API 35/36 矩阵、WAL/崩溃恢复、无障碍和性能基准仍必须在有 Android SDK/设备的环境完成；CI 不得用 debug APK 或成功编译替代这些证据。未配置 `keystore.properties` 时，`bundleRelease` 应继续失败并保留发布阻断，不上传未签名 release 产物。

## 13. iOS 原生桥接收口事实（2026-10-12，基于候选 HEAD `9eeabdf`）

本轮先收口源码契约，不把 Linux 主机上无法运行的 Xcode/Pods/iOS 设备结果写成通过。WatermelonDB 0.28 的 iOS `WMDatabaseDriver` 将裸数据库名解析为 `Documents/<name>.db`，因此 iOS 只读检查必须使用同一解析规则，并以 `sqlite3_open_v2(..., SQLITE_OPEN_READONLY)` 打开；禁止 `CREATE_IF_NECESSARY`、写事务或通过 WatermelonDB adapter 探测未知文件。

新增的 iOS `ZeroReadOnlySqlite` 只实现与 JS preflight 相同的 `probe(databaseName)` 和 `readSnapshot(databaseName)` 合约：数据库名严格限制为 `watermelon`/`watermelon_v4`；只读连接返回 allow-list 表的列、索引、`user_version`、`PRAGMA integrity_check` 和行快照；缺少文件返回 `missing`，权限、锁定、损坏、未知 SQLite 类型和桥接异常全部 reject，交给 JS 的 BootGate fail-closed。该桥接暂不实现 Android 专用的 WAL/SHM backup、target marker、copy/activate/discard，因此 iOS 的 legacy v3→v4 迁移仍会停在可恢复错误页，不能误称为迁移可用。

新增的 iOS `ZeroSecureSecrets` 使用 Keychain generic password 保存 `ai_api_key`，服务名固定、账户名 allow-list、值在 native 层再次 trim/长度校验；读取遇到 `errSecItemNotFound` 返回 `null`，Keychain 错误 reject，删除幂等。API key 不进入 Redux、WatermelonDB、日志或导出。该模块用 React Native Obj-C bridge 自动注册，Xcode 文件引用和 SQLite 系统库链接必须由 macOS/Xcode smoke 验证。

本机可执行的证据只包括源码 contract script、TypeScript/Jest、pbx 引用静态检查；以下仍是外部验收项：`pod install` 生成与 RN 0.87.1/WatermelonDB/Reanimated/Nitro 版本一致、Xcode debug/release 编译、真实 Documents/WAL/权限/锁定 fixture、Keychain 首次解锁/卸载重装生命周期、iOS VoiceOver 和设备启动。未完成这些步骤前，iOS 发布就绪度保持阻断。
