## 目标架构和合并原则

Zero 作为长期维护和质量基线，保留预算、adaptive daily budget、CSV/JSON 导入导出、Zod 校验、诊断页、错误恢复、WCAG 颜色、FlashList、SwipeableRow/撤销、DonutChart、债务和本地优先边界。Zerox 只移植经过审查的中文、收入、二级分类、主题色和 AI 能力，不整支覆盖根目录。

第一阶段保留 `expenses` 与 `incomes` 两张表，在 repository/use-case 输出统一的 `TransactionRecord`。不直接重写为全新的 `transactions` 表，避免同时改变旧 ID、关系、导入导出和所有查询。

所有数据库工作都遵循：只读预检 → 备份 → 新库复制 → 行数/金额/关系/索引/重新打开校验 → 原子切换 pointer。未知 schema、空但已存在文件、未来版本、损坏、锁定和混合结构全部阻塞，不能回退成 fresh。

新安装路径在 P0 中明确为直接创建 v4 target 并写入 verified pointer；`decideDatabasePreflight` 已返回 `fresh-target`，不能让首装先落到没有收入/二级分类的 v3。

3. 定义 JS probe contract，返回 `user_version`、表/列/索引、完整性结果和文件存在性。
4. 为 missing、version 0、future、混合 schema、损坏、WAL 建立双端 fixture 和 hash/mtime 不变断言。

`createAndroidCopyDriver` 已接入 backup snapshot、target writer、adapter close 和 marker-aware discard；迁移 coordinator 负责 target freshness、checkpoint reconcile 和 pointer activation。

Android release 已完成原生编译、Hermes bundle 和 lint，随后因当前主机没有生产签名 keystore 在 packageRelease 校验处停止；真机、正式签名和 iOS 仍未验收。

v4 target 模型、Income 和隔离 `createTargetDatabase` 工厂已准备完成；生产 v3 database.ts 未改变，避免提前打开 v4 adapter。

source-specific `normalizeLegacyRows` 也已落地，Zero/Zerox 的默认字段和 fail-closed 分类 kind 策略已固定；真实 Android SQLite copy 通过 coordinator 接入，设备 reopen 仍待执行。

`copyLegacyRows` 已通过 Android driver 使用 immutable backup snapshot、单次 target batch、read-back verifier 和 target fingerprint；失败后关闭未激活 target 并由下次启动 reconcile，不能称作跨数据库 JS 回滚。

dual-db 状态机已覆盖 activation/activated-marker 不确定性：失败时保持 `verified`，等待下一次启动 reconcile，不把可能已激活的目标误记为 failed。

`runDatabasePreflight` 已把 active pointer、readonly probe 和 decision 组合为可注入 runner，并在 `backend/index.ts` 的 BootGate 前置路径执行；iOS legacy bridge 能只读探测，但缺少完整 copy/activate coordinator 时仍 fail-closed。

隔离 v4 target writer 已基于 Watermelon `prepareCreateFromDirtyRaw` + 单次 batch 实现，保留 id/status/changed；回读失败会丢弃未激活 target，真实 native writer 的完整 coordinator/设备验证仍待完成。

已增加 durable migration checkpoint 契约：MMKV 单键保存 generation、source fingerprint、backup descriptor、target attempt/status 和 target fingerprint；坏 marker、不同 attempt、缺少 verified fingerprint 均 fail-closed。`runAndroidLegacyMigration` 启动时消费该 checkpoint：writing 只 discard/rebuild、verified 只 reopen/reuse，未知 ownership 继续阻塞；没有把 JS `unsafeResetDatabase` 宣称为进程崩溃后的原子回滚。

数据库工厂现在按 active pointer 选择 v3/v4 schema、migrations 和 modelClasses；v4 pointer 会注册 Income/TargetUser/TargetCategory，不再用 legacy v3 model graph 打开 target。native readonly preflight 已先于 adapter 构造，缺失、stale、foreign marker 或 integrity 失败仍阻塞主启动。

预检 runner 现在会在 legacy 文件缺失时继续只读探测 `watermelon_v4`；只有 legacy 与 target 都缺失才返回 `fresh-target`。发现残留 target、target integrity 失败或 target probe 错误都会阻塞，等待 checkpoint marker 和文件生命周期恢复逻辑。

`copyLegacyRows` 现在返回按固定表/字段/row id 顺序生成的 16 位内容指纹，区分缺表与空表并拒绝非有限数字；它用于检测复制前后内容变化，不是密码学完整性哈希，真正的备份和 native reopen 校验仍必须保留。

Android 现在可以只读检查 v4 数据库和 `-wal/-shm` sidecar 的存在、大小与修改时间；未知/孤儿 sidecar 会阻塞。writing target 不会恢复半成品：只有 marker 的 attempt/generation/sourceFingerprint 与 durable checkpoint 完全匹配时，才允许在关闭隔离 JSI adapter 后 identity-guarded discard，再从 immutable backup 重建。

verified target 恢复会通过只读 `user_version=4`、`integrity_check=ok`、八张目标表和 v4 必需列检查，再计算 target row fingerprint；probe 不可用、未知/未来结构或损坏均阻塞。该检查已接入 Android coordinator，设备级 crash/reopen 证据仍待完成。

Android target marker 已加入固定 sidecar：claim 使用 exclusive create + fsync，marker 绑定 generation/attempt/source fingerprint，更新状态只允许 `writing → verified → activated` 单向流转；marker 过大、损坏、临时文件残留、attempt/source 不匹配都会阻塞。AndroidCopyDriver 在 discard 前优先调用显式 closeTarget，缺失时使用 Watermelon JSI 的 `unsafeClose`；close 生命周期不可用就 fail-closed，不删除仍可能被 SQLite 持有的文件。

Android backup bridge 已实现 legacy `watermelon` 的 db/WAL/SHM 复制和按 backupId 的只读快照读取，并已接入 `AndroidCopyDriver.ensureBackup`；只读 integrity 通过后复制，前后 SHA-256、size 和 mtime 不一致就删除备份并失败；descriptor 和快照由 Zod 校验。

`createAndroidCopyDriver` 现在要求 `backupId`，先创建并校验 backup，再从 `readBackupSnapshot(backupId)` 读取 source rows；没有 backup 不允许读取 live source。失败 copy 会先关闭已准备的 target adapter，保留 writing marker 交给下次启动的 reconcile；verified target 通过只读 schema/integrity/fingerprint 校验后可复用，不会在同一成功路径重复构造 JSI adapter。

`copyLegacyRows` 现在同时返回 source fingerprint 和 normalized target fingerprint；后者只能在 read-back verifier 成功后用于 marker 更新，不能替代 native reopen、index 或 integrity 校验。

## 推荐提交顺序

建议形成约 24–26 个 Conventional Commits，提交前固定执行三类审查：

1. `build(native): close rn 0.87 native validation`
2. `feat(db): add readonly sqlite preflight bridge`
3. `feat(migration): copy and verify legacy databases`
4. `fix(boot): gate main navigation on migration recovery`
5. `feat(schema): add unified v4 models and snapshots`
6. `feat(data): add transaction repository and keyed caches`
7. `feat(export): publish export v5 and atomic importer`
8. `feat(domain): migrate income and hierarchical categories`
9. `feat(i18n): add zh-cn and locale parity`
10. `feat(ai): add validated parser and privacy controls`
11. `feat(ai): add idempotent queue recovery and undo`
12. `fix(entry): replace route swap with shared entry mode`
13. `feat(nav): add animated bottom tab bar`
14. `test(ui): add animation and accessibility matrix`
15. `build(native): verify hermes fabric and release artifacts`
16. `ci(migration): add upgrade and export matrix`
17. `ci(release): enforce production readiness gates`

一个提交只能改变一条可验证主线；native、数据库、业务和动画不能混成“大合并提交”。
